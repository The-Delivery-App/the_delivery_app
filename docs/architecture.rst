Architecture
============
 
The app follows a pretty standard client-server setup. The Flutter app talks to the Serverpod backend over HTTP, the server handles all the logic, and everything gets stored in PostgreSQL. Redis sits alongside it for caching and session management.
 
The three packages
------------------
 
the_delivery_app_flutter
~~~~~~~~~~~~~~~~~~~~~~~~
 
This is the mobile app — what users actually see and tap on. It's broken up into a few folders:
 
- screens — one file per screen (feed, basket, restaurant, order status, map, search, account, settings, sign-in, and special deals)
- models — local data models like Food, Order, Basket, Restaurant, and User
- repositories — the data layer, with an interface and implementation for each area (orders, food, account, etc.)
- APIs — service classes that wrap the Serverpod client calls for things like the feed, maps, and orders
- dtos — simple objects used to pass data between the API services and repositories
 
the_delivery_app_server
~~~~~~~~~~~~~~~~~~~~~~~
 
The backend. Each part of the app has its own controller:
 
- feed_controller — serves the browsable feed of food and restaurants
- order_controller — handles placing orders, updating statuses, and tracking
- restaurant_controller — restaurant and menu data
- courier_controller — courier-side order management
- favourites_controller — saving and fetching favourite items
- reviews_controller — submitting and fetching food reviews
- user_profile_controller — profile and address management
- auth_controller — authentication
 
the_delivery_app_client
~~~~~~~~~~~~~~~~~~~~~~~
 
This is auto-generated by Serverpod — don't edit it by hand. If you change anything on the server side (endpoints or models), just run ``serverpod generate`` and it'll update itself.
 
How a request flows through the app
------------------------------------
 
1. The user does something in the Flutter app — say, taps "Place Order"
2. The app calls a method on the generated ``Client`` object, e.g. ``client.order.placeOrder(...)``
3. Serverpod serialises that call and sends it to the server over HTTP
4. The server's order endpoint picks it up and hands it to the ``OrderController``
5. The controller does whatever it needs to in PostgreSQL and sends back a result
6. Serverpod deserialises the response and returns a proper Dart object to the app
